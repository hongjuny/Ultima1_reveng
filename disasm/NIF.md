# NIF — ending image and scroll source

`NIF` is a 7,680-byte data file loaded at `$4000` by `TM $9052`. It contains **192 consecutive rows of 40 Apple II high-resolution graphics bytes**. Each byte contributes seven pixels in least-significant-bit-first order; the high bit is the HGR color-phase bit. A monochrome decode yields a 280×192 rasterized ending text screen. The picture and extracted pixel data stay under private `build/`; [the public extractor](../tools/extract_nif.py) writes `build/data/nif-monochrome.png` and a 7,680-byte phase plane `build/data/nif-phase.bin` locally. Recombining these two planes reproduces every original file byte exactly; `--check` verifies this without writing either artifact.

At `$9073–$9093`, `TM` moves 8,192 bytes from `$4000–$5FFF` to `$6000–$7FFF` and clears the former range. The file provides `$4000–$5DFF`; the other 512 bytes came from prior RAM. The [copy verifier](../tools/verify_tm_victory_gate.py) confirms this overlap. The animation at `$90AA–$9108` reads packed rows from **`$6000–$7DFF` only**. Its source pointer `$90E8/$90E9` starts at `$6000`, advances by `$28` after each row, and is `$7E00` when counter `$6D` reaches zero after 192 rows. The inherited `$7E00–$7FFF` tail is outside the row source. The program resets that pointer to `$6000` before the final key wait `$9132`.

The [render trace](../tools/trace_tm_nif_render.py) independently restored the post-copy state, matched the first row to the private file, and observed its 40 bytes copied to HGR address `$5FD0`, the bottom row of page 2. The next source was `$6028`. At the final key wait, **all 7,680 active HGR bytes on page 1 match `NIF` exactly** when indexed by the Apple II scanline address formula. The [verifier](../tools/verify_tm_nif_render.py) checks source ancestry, row steps, counter, first copy, and full final-page identity. This is an exact image-content contract for a macOS port.

The [intermediate-frame trace](../tools/trace_tm_nif_frames.py) stopped at `$90FE` after each of the 192 row copies and sampled nine stages: 1, 2, 3, 16, 48, 96, 144, 191, and 192 rows. Odd copies write the page-2 bottom row at `$5FD0`; even copies write page 1 at `$3FD0`. At every sampled stage, the **write target page's bottom `n` HGR rows exactly equal the first `n` packed `NIF` rows** in top-to-bottom order. The alternate page may contain an older scroll frame. The emulator's latched video switches report `HIRES=1`, `TEXT=0`, `MIXED=0`, and the **opposite page displayed at `$90FE`**: odd copies find `PAGE2=0`, even copies `PAGE2=1`. On return from the `$90FE` call to `$15AD` at `$9101`, `PAGE2` has toggled to the just-written page at all nine samples. This directly confirms off-screen preparation followed by a page flip. The trace also records all 192 `$90FE` CPU cycle counts: the first interval is 116,977 cycles; the remaining 190 intervals range from 119,167 to 119,254 cycles (mean 119,210.0), and first-to-last copy spans 22,766,880 cycles. These are emulated CPU-cycle measurements, a timing target independent of the host's replay speed. [Verification](../tools/verify_tm_nif_frames.py) checks the source pointer, counter, page selection, sampled lower rows, and cycle profile.

The [final-color trace](../tools/trace_tm_nif_color.py) restored the private `$9132` key-wait state and captured its 560×192 HGR frame. Video switches were `TEXT=0`, `MIXED=0`, `PAGE2=0`, and `HIRES=1`. Applying the same three-bit neighbor and phase rule already checked for the outdoor renderer to the `NIF` bytes predicts **all 107,520 displayed pixels exactly**. The frame uses black (`#000000`), white (`#FFFFFF`), blue (`#0DA1FF`), and orange (`#F25E00`) in this emulator. The [independent verifier](../tools/verify_tm_nif_color.py) reconstructs the color raster from the private `NIF` file and checks the private PNG pixel by pixel; neither artifact is published. This fixes the emulator palette and final-frame raster for a port. Actual analog Apple II composite output, any intermediate-frame color variation, and sound remain separate questions.

For zero-based row `y`, the HGR byte offset within an 8KB page is `((y & 7) << 10) | (((y >> 3) & 7) << 7) | ((y >> 6) * 40)`. The packed file instead uses `y * 40`. At the final frame, placing each packed row at this HGR offset reconstructs page 1 byte-for-byte. The local PNG extractor discards the phase bit and shows only monochrome geometry; it does not claim to reproduce composite color.
