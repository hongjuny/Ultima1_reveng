# MAPCHARS — indoor map glyphs

`MAPCHARS` is a 1024-byte BIN file loaded at `$B000–$B3FF` for town and castle views. It contains 128 glyph codes across eight scanline planes: byte `(scanline × 128) + code` belongs to that code's scanline. The [local extractor](../tools/extract_mapchars.py) reshapes it into 128 arrays of eight original bytes and reconstructs the exact file in its check mode. Its optional JSON output goes only under ignored `build/data/MAPCHARS/`. The high bit of each glyph byte is preserved; its exact color/phase effect has not yet been decoded.

The `STUPH` renderer's self-modified `LDA $0800,Y` at `$1A58` uses `Y = character & $7F`. Its loop selects `$0800/$0880` and then successive pages through `$0B80`, giving scanline addresses `$0800 + 128 × row + code` for rows 0–7. It writes the resulting bytes through two self-modified video addresses; the sampled address and pixel mapping appear below.

That comparison is now available for the first castle glyph, code `$40`. All eight source bytes are `$FF`, and `$7E` (the renderer's XOR byte) was zero. From `$1A58` to `$1A7F`, eight video bytes at `$2081,$2481,…,$3C81` became `$FF`. Replacing **only this one glyph invocation** with eight `$80` bytes, then restoring the font before subsequent glyphs, left exactly those eight video bytes at `$80` at the first castle input. Both replays reached that input at the same cycle and CPU state. The emulator's 560×192 ARGB frame differed in exactly a 14×8 rectangle, `x=14–27,y=8–15`: 112 white pixels versus black. This is one tile's observed display footprint, not a complete color specification.

Additional single-invocation controls used eight `$81`, `$C0`, `$00`, or `$01` bytes. Relative to `$80`, `$81` lit two pixels at `x=14–15` on each row and `$C0` lit two at `x=26–27`; therefore source bit 0 is leftmost and bit 6 rightmost in this sampled glyph, with each bit doubled horizontally in this emulator frame. `$00` looked identical to `$80` for this blank glyph, and `$01` had the same 16-pixel footprint as `$81`. Thus the high bit alone had no visible effect in this particular scene and emulator configuration; its effect with other bit patterns, neighboring bytes, or display settings is still open. The [pixel verifier](../tools/verify_mapchars_glyph_pixels.py) checks the paired snapshots, exact video addresses, and frame effects.

`CAS` loads the file to `$B000`, then its `$9B6E` routine exchanges all 1024 bytes at `$B000–$B3FF` with `$0800–$0BFF`. The map draw at `$9B06–$9B38` calls that routine before and after drawing its 38×18 tile grid. A [runtime trace](../tools/trace_mapchars_render.py) confirmed that `MAPCHARS` was at `$B000` at `$9B09`, at `$0800` at `$9B0C` and the first glyph renderer `$1A58`, then back at `$B000` at `$9B38` and first input `$8A27`. The first renderer read used `Y=$40` and operand `B9 00 08`; video RAM changed during the draw. The [verifier](../tools/verify_mapchars_render.py) checks the source snapshot, code bytes, residency sequence, and final memory. This confirms the castle path; the corresponding town swap is visible in extracted code but has not been replayed here.
