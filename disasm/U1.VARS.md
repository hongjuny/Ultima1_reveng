# U1.VARS — generated player record

`U1.VARS` is created on the separate ProDOS volume `U1.PLAYER` during GEN's confirmed `Y` path. It is a 458-byte BIN with auxiliary load address `$7E6D`. This page records fields observed in the one-character, Human/Male/Fighter replay; the file bytes themselves remain private.

The save helper receives source `$7E6D`, length `$01CA`, and a pointer at `$7E38` to `/U1.PLAYER/U1.VARS`. CiderPress extraction of the disposable player disk matches RAM `$7E6D–$8036` in the post-save snapshot byte-for-byte. Offsets below are relative to the start of the file.

| Offset | RAM address | Observed field | Evidence |
| --- | --- | --- | --- |
| `$0000–$0001` | `$7E6D–$7E6E` | `$01CA` in little-endian order | Observed bytes equal the file length; purpose still open |
| `$004A` | `$7EB7` | Sex ID `0` | GEN sex `A` replay writes `0` here |
| `$004B–$0057` | `$7EB8–$7EC4` | 13-byte name area | Name `A` stored as `$41` followed by zero bytes |
| `$005B–$0066` | `$7EC8–$7ED3` | Six two-byte attribute slots | Low bytes `35,35,10,10,10,15`; high bytes `0` in this replay |

The last 320 bytes are four parallel arrays indexed by one object slot, rather than 80 consecutive four-byte structs. `OUT`'s [byte-matched insertion routine](OUT-object-insert.s) rejects coordinates outside a 64×64 map and an 81st object. It doubles the input tile type before saving it in the map-tile array, combines Y with `$7E70`'s world bits, reads the displaced map byte into the underlying-tile array, writes the object tile to the map, then increments `$7EF6`. The paired controlled replay changed exactly five player-record bytes: the count and slot zero in these four arrays. It also changed exactly the corresponding map cell `(6,7)` from `$04` to `$1E`; the [verifier](../tools/verify_player_object_record.py) checks snapshot ancestry and both effects.

The [byte-matched removal routine](OUT-object-remove.s) searches active slots backward by world/Y and X, or accepts a slot directly at `$997D`. It restores the underlying map byte when the object belongs to the current world, decrements the count, and moves later entries down one position in all four arrays. It also shifts a parallel `$B600` metadata array outside `U1.VARS`. This removal path is currently established from code; a paired runtime removal snapshot is still needed to confirm its effects in a concrete scene. Bytes in slots at or above the count may retain old values, so a port should ignore those slots rather than require them to be zero.

The 137-byte prefix before the object count is only partly classified; possible padding or checksums and many gameplay changes remain to identify. The current checks do not establish whether attribute high bytes are active 16-bit values or reserved storage.

The GEN menu's `B` path calls `$B721` with destination `$6000` and the same path pointer `$7E38`. It checks the loaded file's first two bytes for `$01CA`, then a self-modifying loop copies 458 bytes from `$6000–$61C9` back to `$7E6D–$8036`. Runtime replay confirmed the load and copy against the saved record and reached `$8AC0`, which jumps toward the `OUT` selector. `$6000` is scratch space and changes again before that final breakpoint.

Outdoor `Q` uses [the same save span](OUT-Q-save.s) after recording current outdoor coordinates. Starting from a GEN saved file and one ordinary outdoor Space turn, its disposable player disk gained a record with exactly two changed bytes: offsets `$006D:00→50` and `$0077:95→90`. The record at the Q call, the file extracted afterward, and RAM at the save return all matched byte-for-byte. GEN `B` then loaded that updated file into `$6000`, copied it into the live record, and reached the OUT handoff with all 458 bytes still matching. This is a genuine save-to-reload round trip for changed gameplay state; it does not by itself classify the other 456 bytes or all save triggers. The [verifier](../tools/verify_out_player_save_reload.py) preserves the private file and memory evidence.
