# Apple II 동작에 충실한 macOS 포팅 로드맵

현재 검증 범위와 남은 빈칸은 [종합 리포트](consolidated-report-2026-10-21.md)에 모았다. 이 문서의 단계별 완료 기준은 계속 적용한다.

대상은 이 저장소의 **1986년 Apple II ProDOS판 Ultima I**이다. 목표는 원본의 관찰 가능한 게임 규칙, 데이터 해석, 입력, 화면, 소리, 저장 동작을 설명하고, 같은 조건에서 macOS 구현과 대조할 수 있는 명세를 만드는 것이다. 현재는 이 목표에 도달하지 않았다. 2026-10-21 기준 검토 후 원본 바이트와 재조립 결과가 일치하는 부분은 93개 조각, 3,946바이트이다. 블록 동등 이미지에서 시작부터 `GEN → OUT → CAS/TWN/DNG`까지 재생했고, 성의 이동·전투, 통제된 사망 뒤 `OUT` 부활, 마을 식량 구매의 화폐 경계값, 던전의 1–3층 생성과 일부 몬스터 동작을 확인했다. 여섯 게임 모듈의 첫 한 턴을 비교했고, `OUT`의 B 명령에서 지도·플래그를 통제해 `SPA`/`TM`에 들어가 각각 첫 명령과 다음 입력까지 재생했다. 홀수 의뢰 하나는 자연 입력으로 수락부터 보상까지 연결했고, `TM`의 보석·공격·승리 관문은 통제 실행으로 확인했다. 다른 선행 조건의 정상 획득, 전체 규칙과 결말 표현, macOS 구현과의 비교는 아직 없다. 과거 범위에 대한 시간 예산은 [진행·투입 효율 점검](progress-audit-2026-10-21.md)에 기록했다.

단계 번호는 의존 순서다. 플레이 경로에 필요한 분석은 앞당길 수 있지만, 각 단계의 완료 기준을 생략하지 않는다. 분석 결과에는 항상 [증거 수준](porting-fidelity.md), 파일과 주소, 재현 절차, 미해결 분기를 기록한다.

## 0. 재현 가능한 기준점 확보

- 로컬 추출물의 파일 크기와 SHA-256, 디스크 판본, 도구 버전, 에뮬레이터 설정을 **로컬 매니페스트**에 기록한다. 원본 파일과 원본을 재구성할 수 있는 데이터는 Git에 넣지 않는다.
- 깨끗한 시작 상태, 기존 캐릭터 상태, 주요 장면 진입 상태를 복제 가능한 디스크 이미지나 스냅샷으로 로컬에 마련한다. 입력 시퀀스와 입력 간 프레임 수를 함께 기록한다.
- 어셈블 및 데이터 추출 검증 명령을 한 번에 실행할 수 있게 정리한다. 실패 시 파일, 주소, 차이를 출력한다.

**완료 기준:** 다른 로컬 실행에서 동일 판본과 초기 상태를 확인하고 같은 입력을 재생할 수 있다. 공개 저장소에는 검증 방법과 비민감한 메타데이터만 있다.

## 1. 실행 추적과 메모리 수명 지도

- Apple II 에뮬레이터에서 PC, 레지스터, 메모리 읽기/쓰기, ProDOS 호출, 키보드 및 화면 소프트 스위치를 추적한다. 스냅샷과 입력 기록을 추적 로그에 연결한다.
- `U1.SYSTEM → U1.INTRO → MAKE.INDATA → MI.U1 → STUPH → GEN → OUT`을 먼저 재현한다. `$B703/$B70C/$B733/$B736`의 인자, 반환값, 파일 로드 주소, 실패 경로를 확인한다.
- `$8956` 오버레이 교체 시점과 `$0800`, `$4000` 데이터의 생존 기간을 기록한다. 간접 호출, 자기 수정 코드, 상주 루틴 진입점을 수집한다.
- `TCMAPS` 마지막 768바이트 복사가 파일 끝을 4바이트 넘는 상황에서 실제로 읽는 메모리와 그 바이트의 사용 여부를 관측한다. `CAS` 마지막 슬롯의 초과 4바이트와 첫 입력까지의 무영향 대조 실행은 확인했으며, 이후 사용 여부는 남아 있다.

**완료 기준:** 정상 시작과 메뉴 진입을 주소·파일 로드·메모리 변화로 재현하고, 각 시점의 상주 파일 지도를 제시한다. OS 호출 의미는 추측 없이 기록한다.

## 2. 파일별 코드·데이터 분류와 역어셈블

- 게임 파일마다 코드, 데이터, 빈 공간, 미분류 범위를 주소로 구분한다. `da65` 초안은 출발점으로만 사용하고, Ghidra의 프로그램/오버레이 공간을 분리한다.
- 루틴마다 진입·호출자·피호출자·분기 조건·레지스터와 플래그 계약·읽고 쓰는 상태·반환을 기록한다. 간접 점프와 자기 수정 코드는 런타임 목표 주소를 확인한다.
- 검토한 조각을 `ca65` 소스로 옮겨 원본과 바이트 비교한다. 작은 조각에서 시작해 호출 그래프를 따라 범위를 넓힌다. 주소가 같은 서로 다른 오버레이는 별도로 검증한다.
- 미분류 바이트 수, 검토한 코드 바이트 수, 확인한 간접 대상 수를 파일별로 집계한다. 도달 가능 여부가 불명확한 범위는 완료로 세지 않는다.

**완료 기준:** 플레이와 엔딩에 사용되는 모든 도달 가능 루틴 및 데이터 접근이 분류되고, 포팅에 필요한 루틴의 제어 흐름과 효과가 설명된다. 바이트 일치율은 근거의 한 종류이며, 동작 검증을 대신하지 않는다.

## 3. 상태·데이터 형식 복원

- `$7E00` 부근을 포함한 공유 상태를 필드별 주소, 크기, 초기값, 값 범위, 변경 루틴, 저장 여부로 정리한다. 캐릭터·월드·전투·경제·퀘스트·차량·시간 상태의 소유자를 구분한다.
- `TCMAPS`, `MAPCHARS`, `NIF`, `STUPH`, `MAKE.INDATA`와 각 오버레이 내부 테이블을 구조별로 해석한다. 포인터와 경계 검사를 갖춘 로컬 추출기를 만들고 원본 바이트로 왕복 검증한다.
- 저장/불러오기 파일 구조와 갱신 시점, 오류 처리를 추적한다. 동일 상태에서 저장 후 재시작했을 때 유지되는 필드를 확인한다.
- 화면용 데이터와 게임 규칙용 데이터를 구분한다. 공개 문서에는 형식과 변환 절차를 기록하고, 원본 데이터를 재구성할 수 있는 덤프는 게시하지 않는다.

**완료 기준:** 각 데이터 레코드와 상태 필드의 소비자·생산자가 식별되며, 로컬 추출/재인코딩과 저장/불러오기 왕복이 일치한다. 의미를 모르는 바이트는 명시한다.

## 4. 게임 루프와 규칙 명세

게임의 실제 진행 순서에 맞춰 다음 경로를 분석한다.

1. `GEN`: 신규 캐릭터 생성, 선택지, 초기 자원, 이어하기, 유효성 검사.
2. `OUT`: 입력 처리, 이동과 턴 소비, 지형, 조우, 마을·성·던전·우주 진입, 사망과 저장.
3. `TWN`/`CAS`: 지도, NPC, 상점, 가격과 재고, 퀘스트, 전투, 출입 조건.
4. `DNG`: 층·방향·시야, 몬스터, 함정과 보물, 전투 계산, 탈출.
5. `SPA`/`TM`: 발사·연료·방어막·항법·도킹, 시간 여행, 최종 전투, 승리 조건과 종료.

각 명령에 대해 **입력 → 전제 조건 → 상태 변화 → 화면/소리 → 다음 상태**를 표로 만든다. 난수 생성기와 시드, 오버플로/부호/BCD, 턴과 프레임 타이밍을 확인한다. 중요한 분기는 경계값과 실패 입력까지 시험한다.

**완료 기준:** 새 게임부터 승리·패배·재시작까지의 주요 경로를 주소 근거와 에뮬레이터 시나리오로 설명한다. 명령별 상태 변화와 예외가 포팅 명세에 들어간다.

## 5. Apple II 표현과 입출력 명세

- 키 코드, 키 누름 유지/반복, 입력 대기 중 시간 진행을 확인한다.
- 텍스트 및 그래픽 모드, 메모리 페이지, 문자·타일 변환, 색상과 화면 갱신 순서를 기록한다. 대표 장면을 원본 화면과 프레임 단위로 비교한다.
- 스피커 토글, 음 높이와 길이, 무음 구간을 캡처한다. CPU 속도에 묶인 루프가 게임 규칙이나 애니메이션에 영향을 주는지 확인한다.
- ProDOS 또는 하드웨어의 관찰 가능한 결과를 정의한다. 내부 구현을 그대로 복제할 필요는 없지만, 게임에서 보이는 효과는 보존한다.

**완료 기준:** 입력, 화면, 소리, 타이밍의 기준 장면과 측정법이 있으며 macOS 쪽에서 자동 또는 수동으로 대조할 수 있다.

## 6. 비교 가능한 macOS 구현

- 먼저 원본 규칙과 데이터를 읽는 코어를 만들고, 렌더링·입력·저장을 분리한다. 상태 스냅샷 및 결정적인 입력 재생 인터페이스를 제공한다.
- 각 기준 시나리오를 원본과 포트에서 실행하여 명령 후 상태, 화면, 소리, 저장 결과를 비교한다. 차이는 의도한 현대화인지 결함인지 기록한다.
- macOS에 맞는 창 크기, 접근성, 키 설정 같은 개선은 원본 동작과 구분 가능한 옵션으로 설계한다. 기본 충실도 모드의 규칙은 검증된 Apple II 동작을 따른다.

**완료 기준:** 아래 수용 기준을 통과하고, 미해결 차이와 의도한 변경을 사용자가 볼 수 있다.

## 포팅 준비 수용 기준

| 항목 | 통과 조건 |
| --- | --- |
 실행 경로 | 시작·새 게임·이어하기·각 주요 모듈·승리·패배 경로가 추적되고 재현된다. |
 규칙 | 각 명령의 전제 조건, 상태 변화, 난수·경계값이 주소와 시나리오로 확인된다. |
 데이터 | 사용되는 레코드의 구조와 참조 관계가 확인되고 로컬 왕복 검증이 통과한다. |
 저장 | 저장·불러오기·재시작 결과가 동일 상태로 검증된다. |
 표현 | 대표 장면의 입력 응답, 화면, 소리, 타이밍 비교 기준이 있다. |
 불확실성 | 미분류 범위와 관측되지 않은 분기가 목록에 남고, 포팅 결과에 영향을 주는 미해결 항목은 없다. |

## 바로 다음 작업 묶음

1. [실행 구조](execution-architecture.md)의 공용 엔진·각 모듈 메인 루프·입력/표시/소리/파일 I/O 연결을 주소와 실행 근거로 완성한다. `STUPH` 진입 벡터와 키 입력부터 화면까지의 한 프레임을 먼저 추적한다.
2. 모듈·명령·분기·상태 필드별 증거 장부를 만들고, 추적 스크립트와 비공개 스냅샷의 의존 관계를 표시한다.
3. [의뢰·최종 탈것 상태 흐름](quest-and-final-craft.md)의 정적 연결을 실제 플레이로 재현한다. 홀수 의뢰 1의 수락·던전 완료·빨간 보석 수령은 정상 입력으로 연결됐다. 나머지 보석, 공주 경로, 생성된 탈것 탑승을 잇는다. `TM`의 보석 파괴·방향 공격·승리 관문·`NIF` 로드와 1·2단계 전환은 통제 실행으로 확인됐다. 몬데인과의 일반 플레이 완주는 분석의 우선순위에서 내려놓고, 승리 분기와 결말 표시의 계약을 통제 입력으로 검증한다.
4. 공용 서비스 지도를 바탕으로 시나리오를 묶어 각 모듈의 명령·데이터·저장 규칙을 채운다. `TCMAPS` 마지막 슬롯의 초과 4바이트는 상속된 RAM 값으로 확인했고, 첫 입력까지는 해당 4바이트를 지워도 다른 메인 RAM 차이가 없었다. 이후 소비자와 다른 진입 상태는 계속 확인한다.

작업 기록은 [분석 로그](analysis-log.md), 주소 근거는 [파일별 페이지](../disasm/README.md)에 남긴다. 우선순위와 시간 예산은 [진행·투입 효율 점검](progress-audit-2026-10-21.md)을 따른다.
