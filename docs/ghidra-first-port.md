# Ghidra 우선, 주소 대응 방식의 포트 작업

## 작업 단위

1986년 Apple II 게임의 각 파일을 별도 Ghidra 프로그램으로 유지한다. 같은 `$8956`에 올라오는 일곱 오버레이를 하나의 연속 주소 공간으로 합치지 않는다. Ghidra가 제시한 명령을 [내보내기 도구](../tools/ghidra/export_instructions.py)로 `build/ghidra-project/FILE-instructions.tsv`에 기록한다. 각 행은 원래 주소, 끝 주소, 원본 바이트, 명령, 피연산자, 흐름 대상, fallthrough, 소속 함수 후보를 갖는다. 내보내기 직후 모든 명령 바이트를 `extracted/FILE`과 대조한다. TSV와 원본 바이트를 담은 생성물은 비공개 `build/`에 둔다.

**이 대조는 Ghidra의 해석이 옳다는 증거가 아니다.** 인라인 문자열, 그림, 주소표를 명령으로 읽은 행도 원본 바이트와 일치한다. 따라서 주소별 상태는 `확정 코드 / 확정 데이터 / Ghidra 코드 후보 / Ghidra 데이터 후보 / 미분류`로 계속 구분한다. [기존 장부](code-data-ledger.md)의 숫자를 코드 완료율로 간주하지 않는다.

첫 전체 내보내기에서는 12개 프로그램의 **명령 후보 8,829개, 19,660바이트**가 원본 파일과 바이트 일치했다. 그 목록에서 이미 실행으로 확인한 `SPA $9700` 격추 보상 코드가 빠진 것을 발견했다. 앞선 `JSR`의 인라인 문자열을 데이터로 표시하고 실제 복귀·분기 주소를 시드한 뒤 SPA를 다시 분석했다. 재분석 결과 SPA는 **1,364개 후보 명령·3,064바이트**로, 기존보다 83개·184바이트 늘었고 `$9700/$9732/$973A`가 목록에 나타났다. 전체는 **8,912개 후보 명령·19,844바이트**다. 이 값은 장부의 검증 코드 4,221바이트와 Ghidra 미검증 명령 후보 15,623바이트를 합한 것이다. 명령 후보의 주소 목록을 얻은 것은 진전이지만, 87,012바이트 실행 파일 중 나머지를 코드 아닌 것으로 판정했다는 뜻은 아니다. 같은 파일에서 내보내기를 반복하지 않고 검사만 하려면 `python3 tools/ghidra/export_instructions.py --check`를 실행한다.

첫 번역 조각은 [Swift `SpaceHitPort`](../port-prototype/SpaceHit.swift)이다. 확인된 명중 뒤 `SPA $9700–$9741`의 선택된 적 바이트 감소, 16비트 경험치 100 증가와 상한, 격추 수 255 포화, 20회 분기와 마지막 `CMP`의 C/Z/N을 원본 메모리 주소에 대응시켰다. [대조 도구](../tools/verify_port_space_hit.py)는 Ghidra가 주요 진입점 세 곳을 명령으로 내보냈는지 먼저 확인하고, 통제 에뮬레이터의 `0→1`, `19→20` 명중 전후 상태와 Swift 결과를 비교한다. 경험치·계수 포화 경계도 검사한다. 이 조각에는 호출자, 그래픽, 소리, 전체 레지스터 수명이 포함되지 않는다. 따라서 이것은 완성된 `SPA` 포트가 아니라 **주소 대응 번역과 누락 지점 발견을 반복할 수 있는 첫 단위**다.

이후 실제 게임 시작부터 [macOS 초기화 화면](native-startup.md)을 구현했다. `U1.INTRO`, `MAKE.INDATA`, 재배치된 `$8700` 지원 코드를 별도 Ghidra 시작 프로젝트에서 분석하고 1,171개 명령 후보를 주소별 Swift 블록으로 옮겼다. 네이티브 앱이 직접 로드·압축 해제·화면 구성을 수행하며 세 비교 시점의 두 HGR 페이지와 색상 래스터를 원본에 대조한다. 앞으로의 번역 순서는 이 시작 화면에서 `MI.U1/STUPH/GEN`으로 이어지는 실제 흐름이다.

## 일대일 번역 계약

첫 macOS 구현은 Swift로 만들되, 각 번역 단위에 원본의 `파일:주소`를 붙인다. 단위는 Ghidra가 제시한 함수 전체가 아니라 **진입점과 모든 출구를 설명할 수 있는 기본 블록 또는 루틴**이다. 코드를 옮길 때 다음을 함께 적는다.

1. 진입 PC와 읽고 쓰는 A/X/Y/P/SP, 제로 페이지, 상주 메모리, 플레이어 레코드.
2. 원본 분기·호출·간접 대상과 Swift의 대응 대상. 자기 수정 명령은 변경되는 바이트와 재실행 시의 의미를 별도 상태로 둔다.
3. `JSR` 뒤 인라인 데이터의 정확한 길이·소비자·복귀 주소. 이를 명령으로 번역하지 않는다.
4. ProDOS/ROM/스피커/키보드/그래픽 주소 접근의 계약. 화면과 소리는 공용 어댑터에서 처리하되 원본 메모리·타이밍 효과를 추적할 수 있게 한다.
5. 번역 결과가 아직 없으면 `미번역`, 코드/데이터가 불확실하면 `경계 미확정`, 호출 대상이 빠졌으면 `대상 미해결`로 기록한다. 실행 가능한 기본값으로 조용히 건너뛰지 않는다.

이렇게 하면 먼저 **동작을 보존하는 직역**을 만들고, 각 주소가 설명된 뒤 Swift의 화면·입력·저장 계층으로 정리할 수 있다. 직역 단계의 목적은 미해결 주소를 강제로 드러내는 것이다. 게임을 정상 플레이로 오래 진행하는 것은 번역된 블록의 대조 검증에 쓰고, 파일 전체 분류를 대신하지 않는다.

## 완료 기준과 우선순위

파일마다 전체 바이트를 `코드 / 데이터 형식 / 패딩 / 미확정` 중 하나로 설명하고, 모든 도달 가능한 호출·분기·간접 대상에서 번역된 루틴 또는 명시적인 외부 계약으로 이어지게 한다. 각 번역 단위는 같은 초기 상태와 입력에 대해 원본 에뮬레이터의 상태 변화와 화면/소리 사건을 비교한다. `Ghidra 함수 수`, `후보 명령 수`, `Swift 줄 수`는 완료 지표가 아니다. 핵심 지표는 **미확정 바이트, 미해결 간접 대상, 번역되지 않은 도달 가능 블록**의 감소다.

시작 순서는 `STUPH` 입출력·화면·소리 서비스와 `MI.U1` 공용 상태를 먼저 옮기고, `GEN→OUT`의 한 번의 입력 턴을 실행 가능한 세로 단면으로 만든다. 그다음 `CAS/TWN/DNG/SPA/TM`을 별개 오버레이로 더한다. 큰 `MAKE.INDATA`와 데이터 파일은 명령 수로 판단하지 않고 복사·디코딩·그림/지도 형식을 먼저 분리한다. 이 순서는 기능이 완성된 모듈만 골라 세는 방식이 아니라 공용 의존성을 먼저 닫기 위한 작업 순서다.

공개 저장소에는 내보내기·번역 도구와 독자적인 분석·구현을 두고, 원본 바이너리와 원본 바이트를 대량으로 담은 Ghidra TSV/생성 목록은 `build/`에만 둔다.
