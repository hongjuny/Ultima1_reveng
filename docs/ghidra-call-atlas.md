# Ghidra 호출 지도와 검토 경계

2026-10-21에 Ghidra 12.1.4의 `6502:LE:16:default` 언어로 시작 파일 세 개, `MI.U1`, `STUPH`, 일곱 게임 오버레이를 각각 **독립된 프로그램**으로 가져왔다. ProDOS 카탈로그의 로드 주소를 적용하고 실행 관측 지점, 바이트 일치 조각, 검증된 간접 주소표의 로컬 대상, `STUPH` 벡터를 진입점으로 지정했다. 인라인 인자와 주소표는 분석 전에 데이터로 정의했다. 프로젝트, 자동 분석 결과 TSV, 로그는 비공개 `build/ghidra-project/`에 둔다. [재현 스크립트](../tools/ghidra/import_modules.py)는 로컬 `extracted/`가 있을 때 같은 작업을 반복한다.

## 얻은 것과 아직 얻지 못한 것

| 프로그램 | 로드 주소 | Ghidra 함수 후보 | 함수 본문에서 발견한 직접 호출 | 그중 `MI.U1` 주소 | 그중 `STUPH` 주소 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `U1.SYSTEM` | `$2000` | 3 | 8 | — | — |
| `U1.INTRO` | `$0800` | 28 | 32 | — | — |
| `MAKE.INDATA` | `$1E00` | 6 | 6 | — | — |
| `MI.U1` | `$7000` | 38 | 76 | 50 | 22 |
| `STUPH` | `$0800` | 89 | 45 | 0 | 33 |
| `GEN` | `$8956` | 19 | 74 | 27 | 25 |
| `OUT` | `$8956` | 54 | 126 | 46 | 15 |
| `CAS` | `$8956` | 43 | 117 | 43 | 28 |
| `TWN` | `$8956` | 39 | 99 | 40 | 16 |
| `DNG` | `$8956` | 63 | 152 | 44 | 19 |
| `SPA` | `$8956` | 61 | 174 | 54 | 37 |
| `TM` | `$8956` | 61 | 136 | 37 | 13 |
| **합계** | | **504** | **1,045** | | |

이 숫자는 **Ghidra가 인식한 함수 본문에 대한 후보 통계**다. 도달 가능한 코드 전체, 역어셈블 완료율, 실제 실행 호출 횟수가 아니다. 이 실행은 기존에 바이트 일치로 검증한 조각의 시작 주소도 진입점으로 넣었다. 마지막 두 열은 공용 엔진이 상주하는 게임 단계에서만 분류했다. 시작 단계의 같은 주소에는 다른 파일이 있을 수 있다. `JSR` 뒤 인라인 문자열·인자를 쓰는 게임이므로 데이터 바이트가 가짜 명령이나 호출로 해석될 수 있다. 진입점을 보강하기 전에는 `CAS $993C→$7441`, `TWN $9A29→$7747`, `OUT $984B→$7461` 같은 가짜 직접 호출이 보였고, 보강 후 목록에서는 사라졌다. 남은 후보도 실행 사실로 승격하지 않는다.

기본 진입점만 넣은 첫 실행에서는 212개 함수 후보와 513개 직접 호출을 얻었다. 검증 조각의 시작점만 추가한 중간 재분석은 299개와 705개였다. 그때 검증 조각 3,191바이트 가운데 3,081바이트만 명령으로 표시했고, 인라인 인자를 명령으로 오독하는 곳도 있었다. 이어 인라인 인자를 데이터로 고정하고 **여섯 주소표의 로컬 핸들러와 34개 `STUPH` 벡터**를 진입점으로 주었다. `SPA` 방향 핸들러의 인라인 표시 인자·방향표와 `STUPH`의 소리 진입표도 데이터로 지정하고, 소리 효과 아홉 곳을 간접 진입점으로 넣었다. 이어 `SPA V` 항법 화면의 **두 번째 26개 명령 포인터 표** `$9BCB`를 데이터로 고정하고 로컬 대상도 진입점으로 지정했다. SPA 후보는 36개/101개에서 61개/174개로 늘었다. 현재 합계 504개/1,045개는 이 보강 후의 **후보 수**다. [코드·데이터 장부](code-data-ledger.md)는 검증 코드 4,112바이트와 검증 데이터 476바이트가 모두 Ghidra 분류와 일치함을 확인하지만, 그 밖의 파일 내용을 해결한 것은 아니다.

공용 키 표 26바이트와 여섯 오버레이의 일반 핸들러 포인터 156개, `SPA V`의 별도 포인터 26개를 Ghidra 데이터로 정의했다. [명령 디스패치 행렬](command-dispatch-matrix.md)과 [항법 화면 표](spa-view-commands.md)는 Ghidra가 읽은 182개 대상 주소를 원본의 리틀 엔디언 값과 교차 검증한다. 표를 통한 간접 진입은 위 **1,045개 직접 호출**에 포함되지 않는다. `STUPH`의 아홉 소리 효과도 스택에 복귀 주소를 넣은 뒤 `RTS`로 진입하므로 직접 호출 목록 밖에 있다. 간접 대상에서 시작하는 함수 본문이 새로 분석되면서 그 본문 **내부의 직접 호출**은 늘었다.

## 게임의 연결된 실행 경로

아래 주소는 자동 결과만 옮긴 것이 아니라 기존 바이트 재조립·에뮬레이터 추적과 대조한 중심 경로다. `A → B`는 주소 A의 호출이 주소 B로 이어짐을 뜻한다.

| 단계 | 이어지는 루프와 공용 서비스 | 확인 근거 |
| --- | --- | --- |
| 부트 → 공용 엔진 | `U1.SYSTEM → U1.INTRO → MI.U1 $7000`; 초기 로더 `$8956`을 거쳐 `STUPH`, `GEN`을 로드 | [부트·파일 로드 관계](dependency-map.md). `MI.U1 $7000`을 Ghidra는 `$8956` thunk로 표시하지만, 그 주소는 첫 게임 오버레이가 올라오면 교체된다. |
| `GEN` → `OUT` | 생성·불러오기 메뉴 `$89FD`; 불러온 상태를 `$7E6D–$8036`에 복원하고 `$8AC0 → $88FB` | [GEN 실행 기록](../disasm/GEN.md), [플레이어 기록](../disasm/U1.VARS.md) |
| `OUT` 반복 | `$89A1 → MI.U1 $836E` 상태 표시; `$8A6C → STUPH $15C5` 키; `$89CB → MI.U1 $82A2` 명령 해석; 모듈별 포인터 표와 후처리 후 반복 | [야외 루프](execution-architecture.md), [OUT 기록](../disasm/OUT.md) |
| `CAS` 반복 | `$89EE → $836E`; `$8A27 → $15C2`; `$8A1F → $82A2`; 성 내부 핸들러와 `$9804` 후처리 | [CAS 실행 기록](../disasm/CAS.md) |
| `TWN` 반복 | `$89EC → $836E`; `$8A1E → $15C2`; `$8A16 → $82A2`; 상점 핸들러와 `$9F07` 후처리 | [TWN 실행 기록](../disasm/TWN.md) |
| `DNG` 반복 | `$8DDA → $15C2` 키; `$8D99` 입력·명령; `$98EC` 몬스터/턴 처리 후 반복 | [던전 루프](execution-architecture.md), [키 폴 재조립](../disasm/DNG-key-poll.s). 키 호출은 자동 목록에서 누락됨. |
| `SPA` 반복 | `$8A5F → $15C2`; `$8A67 → $82A2`; 자체 핸들러 표와 `$8AB3` 상태 갱신. `V`는 `$9361` 별도 입력 루프·`$9BCB` 표·`$93D8` 패치 호출 | [SPA 실행 기록](../disasm/SPA.md), [항법 명령](spa-view-commands.md) |
| `TM` 반복 | `$8E6A → $836E`; `$8E8E → $82A2`; 자체 `$9815` 입력과 핸들러 표 | [TM 실행 기록](../disasm/TM.md) |

`MI.U1 $7000–$8955`는 게임 중 공용 코드로 남고, `STUPH`의 `$15xx` 진입 벡터가 입력·화면·난수·파일 서비스를 제공한다. 오버레이 일곱 개는 모두 `$8956`부터 시작하므로 **각 모듈의 호출 그래프는 그 모듈이 로드된 순간에만 유효**하다. 모듈 이동은 공용 선택기 `$88F8–$893E`가 파일을 다시 읽는 전환이며, 한 정적 그래프에서 오버레이들을 동시에 연결하면 잘못된 호출 관계가 생긴다. [의존 관계 지도](dependency-map.md)와 [검증된 어셈블리 주소표](assembly-atlas.md)를 함께 읽어야 한다.

## 다음 검토 단위

1. [코드·데이터 장부](code-data-ledger.md)의 후보·미분류 구간을 실제 호출자, 인라인 데이터, 화면 데이터에 맞춰 교정한다. 검증된 구간 밖의 함수 시작·끝은 아직 후보로 둔다.
2. `MI.U1` 공용 함수와 `STUPH` 벡터의 호출자를 모듈별로 연결하고, [간접 핸들러 행렬](command-dispatch-matrix.md)의 각 대상에 실제 효과와 [제로 페이지 수명](memory-and-zero-page.md)을 붙인다.
3. 대표 한 턴을 키 래치 → 명령 해석 → 핸들러 → 상태 갱신 → 화면/소리까지 주소와 메모리 효과로 닫는다. 이 경로를 macOS 포트의 첫 비교 사양으로 사용한다.

현재 [검증된 어셈블리 주소표](assembly-atlas.md)는 96개 조각, 중복을 뺀 4,096바이트다. 이것은 전체 역어셈블 결과가 아니다. 이 지도는 큰 뼈대를 명시하지만, 아직 각 함수와 데이터의 전 범위를 완전히 분류하지 못했다.
