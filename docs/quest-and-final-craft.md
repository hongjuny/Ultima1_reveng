# 성 의뢰에서 시간 이동 탈것까지

이 문서는 원본 바이너리에서 확인한 **생산자 → 상태 → 소비자** 경로를 모은다. 아래 주소와 조건은 [로컬 바이트 검증](../tools/verify_quest_flags.py)을 통과한다. 최종 탈것의 `OUT` 생성 부분은 [한 바이트 통제 실행](../tools/verify_final_craft_spawn.py)으로도 확인했다. 성 의뢰 완료부터 공주 경로를 거쳐 `TM`까지 자연스럽게 잇는 재생은 아직 없다.

## 여덟 성 의뢰

`CAS` 진입 시 `$896B–$898C`는 야외 위치 번호 `$7EED`를 21 단위로 줄이고 세계 구역 `$7E6F`의 두 배를 더해 성 인덱스 `$9E3B`를 만든다. 짝수 결과는 `6 − 결과`로 뒤집는다. 따라서 이 인덱스는 `0–7`이다. `$9437`에서 의뢰를 받으면 `$7EA9 + 인덱스`를 0에서 1로 올린다. 이미 양수면 다시 받지 않는다. 완료 생산자는 양수인 항목만 `$FF`로 바꾼다. `$92CC`의 성 보상 진입은 그 음수 표시를 검사하고, `$94E7`에서 항목을 0으로 되돌린 뒤 보상한다.

첫 성의 통제 실행은 이 수락 경로를 확인했다. 첫 입력 스냅샷의 성 내부 좌표 `(0,9)`만 왕의 `$6C` 타일 `(31,6)`으로 바꾸고 `T`(대화), `S`(봉사)를 입력했다. 실행은 `$927C → $92AA → $92CC → $93FB → $9437 → $943A`에 도달했고, 인덱스 6의 `$7EAF`가 `0→1`로 바뀌었다. 다른 일곱 의뢰 바이트는 0이었다. [비공개 스냅샷 검증기](../tools/verify_cas_quest_accept.py)가 타일·입력·주소·상태를 확인한다. 왕에게 걸어가는 경로와 이후 보고는 이 실험에 포함되지 않았다.

두 번째 성의 홀수 의뢰는 **메모리 변경 없이** 수락했다. 첫 `OUT` 입력 `(39,33)`부터 방향키 38번으로 원시 타일 `$08`인 `(22,20)`에 도착하고 `E`를 눌렀다. `CAS`는 야외 위치 번호 1, 세계 구역 0에서 성 인덱스 1을 계산했다. 성 입구 `(0,9)`에서 오른쪽 25번, 위쪽 3번을 눌러 왕의 `$6C` 타일 `(25,6)`에 도착했다. 이동 중 HP는 150, 여덟 의뢰 상태는 모두 0으로 유지됐다. 이어 `T`, `S`는 `$927C → $92AA → $92CC → $93FB → $9437 → $943A`를 거쳐 `$7EAA:0→1`을 만들었다. [전체 입력 계보 검증기](../tools/verify_odd_castle_quest_accept.py)는 38개 야외 이동, 성 진입과 로드, 28개 성 내부 이동, 왕의 응답과 상태 변경을 각 비공개 스냅샷으로 확인한다.

수락 직후 왕의 문구를 Space로 넘기고 성의 다음 입력을 받았다. 왔던 길을 방향키 28번으로 되돌아가 출구에서 Left를 누른 뒤 `OUT`을 다시 로드했다. 의뢰 1은 계속 `$7EAA=1`이었다. 야외 `(22,20)`에서 26회 이동해 원시 `$0E` 던전 타일 `(43,15)`에 도달하고 `E`로 `DNG`를 로드했다. 첫 던전 입력에서 깊이 1, 로컬 좌표 `(1,1)`, 의뢰 상태 `[0,1,0,0,0,0,0,0]`을 확인했다. [성에서 던전까지 검증기](../tools/verify_odd_quest_to_dng.py)는 각 이동·오버레이 전환·스냅샷 계보를 확인한다. 여기까지는 의뢰 수락 바이트의 주입 없이 정상 입력만 사용했다.

| 성 인덱스 | 완료 생산자 | 완료 조건 | 성 복귀 보상 |
| --- | --- | --- | --- |
| `0,2,4,6` | `OUT $913A–$9169` | `$7EED`가 `$9D9C`의 8개 랜드마크 번호 중 해당 짝수 의뢰와 연결된 값에 일치하고 의뢰 상태가 양수 | `$94E7`에서 힘 증가 경로 |
| `1,3,5,7` | `DNG $94A7–$94C8` | 몬스터 종류 `$A52E=5`, 던전 깊이 `$A506`에 대응한 의뢰 상태가 양수 | `$959D → $95BC`의 보석 경로 |

야외의 8개 번호 중 4개는 완료 대상 인덱스가 `$FF`라서 의뢰를 완료하지 않는다. 나머지는 순서대로 `6,4,2,0`에 연결된다. 던전의 계산은 `((깊이−1) >> 1) × 2 − 1`이므로 깊이 3–4, 5–6, 7–8, 9–10에서 각각 인덱스 `1,3,5,7`을 가리킨다. 깊이 1–2는 계산 직후 분기로 완료를 건너뛴다. 깊이 10을 넘는 정상 플레이 동작은 여기서 확인하지 않았다.

짝수 의뢰의 완료도 한 경우 실행했다. 첫 `OUT` 입력 스냅샷에서 야외 위치만 실제 랜드마크 타일 `(59,3)`으로 옮기고 의뢰 0 바이트 `$7EA9`를 `0→1`로 놓았다. 원래 지도 셀은 `$0A`였다. `E` 입력은 `$90C8 → $913A → $915F → $9162`를 지나 위치 번호 `$7EED=2`와 의뢰 상태 `$7EA9=$FF`를 남겼다. [비공개 스냅샷 검증기](../tools/verify_out_landmark_quest.py)는 지도 타일과 선택된 번호, 오직 대상 의뢰 바이트의 완료 값을 확인한다. 의뢰 0을 정상 플레이에서 수락한 뒤 해당 랜드마크까지 이동한 경로는 아직 없다.

홀수 의뢰를 성에 보고하면 `$7E6F` 값이 네 보상 루틴 중 하나를 고른다. 루틴은 `$7E75,$7E76,$7E77,$7E78`을 각각 증가시키며, 인접 문구는 차례대로 빨강·초록·파랑·하양 보석을 지칭한다. `OUT $8D73–$8D8A`의 시간 이동 탑승 분기는 **네 바이트가 모두 0이 아닌지** 검사한다. 성공 뒤 `TM` 오버레이 선택값은 `$18`이다. 이 관문과 `TM` 진입은 네 바이트를 통제한 [실행 실험](turn-contracts.md#오버레이-진입-증거)으로도 확인했다.

첫 보석 보상은 먼저 통제 실행으로 확인했다. 첫 성 입력 스냅샷에서 왕의 타일 좌표, 홀수 의뢰 인덱스 1, 해당 완료 바이트 `$7EAA=$FF`를 놓고 `T`를 입력했다. `$92AA → $92CC → $94E7 → $959D → $95BC → $963A`를 지나 `$7EAA`가 0으로 초기화되고 빨간 보석 `$7E75`가 `0→1`이 됐다. [통제 실행 검증기](../tools/verify_cas_gem_award.py)가 입력, 분기, 상태를 확인한다. 아래의 연속 경로에서 같은 보상을 메모리 개입 없이 재현했다. 다른 세 보석의 실제 획득은 아직 없다.

던전의 홀수 완료 쓰기도 처음에는 통제 실행으로 확인했다. 이미 확인한 1층 치명타 경로를 `$94A7`까지 그대로 실행한 다음, 검사 대상 몬스터 종류 `$A52E:1→5`, 깊이 `$A506:1→3`, 의뢰 1의 상태 `$7EAA:0→1`을 바꿨다. `$94C3`의 쓰기는 `$7EAA:1→$FF`를 만들었다. [검증기](../tools/verify_dng_odd_quest.py)는 원래 처치 스냅샷에서 시작한 입력과 변경한 세 바이트, PC, 완료 상태를 확인한다.

이후 실제 3층 몬스터로도 같은 결과를 재현했다. 정상 입력으로 도달한 3층 첫 입력 스냅샷에서 **의뢰 수락 바이트 `$7EAA` 하나만** `0→1`로 바꿨다. 원래 생성된 슬롯 5 몬스터는 `(7,5)`, HP 30이었다. 뒤돌기 `$0A` 후 몬스터가 `(7,4)`로 이동했고, `A` 두 번으로 HP가 `30→2→처치`됐다. 처치 직후 `$7EAA=$FF`; 원래 셀 `$54`는 `$04`로 복원되고 같은 슬롯은 `(9,7)`에 HP 40으로 재생성됐다. 플레이어 HP는 108로 유지됐다. [3층 재생 검증기](../tools/verify_dng_level3_quest_hunt.py)가 출발 스냅샷의 단일 바이트 개입, 세 입력의 계보, 네 단계 몬스터 상태와 의뢰 완료를 확인한다.

이제 **의뢰 수락부터 3층 완료까지 메모리 개입 없는 연속 경로**도 확인했다. 위의 두 번째 성 경로에서 던전 1층으로 들어가 지도를 매 턴 다시 읽으며 17회 입력으로 첫 계단, 24회 입력으로 다음 계단에 도달했다. 3층의 첫 생성에서는 슬롯 5가 비활성이었다. 2층 계단 위에서 Space 두 번을 입력한 분기는 3층 입장 시 슬롯 5를 `(6,1)`, HP 45로 활성화했다. 이때 플레이어 HP는 28이었다. 3층에서 Up, `A`, `A`를 입력하자 슬롯 5가 `(7,1)`로 이동하고 HP가 `45→10→처치`됐으며, 마지막 공격 핸들러에서 `$7EAA:1→$FF`가 됐다. 플레이어 HP는 28로 유지됐다. [연속 경로 검증기](../tools/verify_odd_quest_natural_completion.py)는 두 층의 모든 입력과 계단 전환, Space 분기의 계보, 실제 슬롯 5 처치와 의뢰 상태를 비공개 스냅샷으로 검증한다.

완료 뒤 자연 입력으로 **성 보상까지** 이어 갔다. 3층 출구의 `$08` 계단은 슬롯 1 몬스터가 점유했다. 방향 전환·이동 시도·공격 두 번 뒤 플레이어 HP가 5가 됐고, 이어 Space 두 번으로 던전 사망 분기 `$98DD`에 들어갔다. 이때도 `$7EAA=$FF`였다. `$88FD`가 `OUT`을 선택하고 부활 루틴이 HP·식량을 각각 99로 채웠으며, 야외 `(8,47)`에서 완료 표시가 그대로 남았다. 여기서 방향키 73번으로 두 번째 성 `(22,20)`에 돌아와 `E`, 성 내부 방향키 28번, `T`를 입력했다. 왕의 `$92AA → $92CC → $94E7 → $959D → $95BC → $963A` 경로는 `$7EAA:$FF→0`, 빨간 보석 `$7E75:0→1`을 만들었다. [복귀·보상 검증기](../tools/verify_odd_quest_natural_gem_award.py)는 사망/부활과 모든 이동·오버레이·보상 스냅샷의 계보를 검사한다. 따라서 이 한 의뢰의 수락·처치·보상은 모두 실제 게임 입력으로 연결됐다. 이 경로의 사망 페널티 및 저장 후 지속성은 별도로 확인해야 한다.

## 최종 탈것의 생산 경로

`CAS`의 왼쪽 출구 중 `$8AC1`로 들어가는 경로에는 공주 관련 메시지와 상태 보상 코드가 있다. `$8B38–$8B64`는 HP·Coin·경험치에 각각 500을 더하고 9999에서 상한을 둔다. `$8B65–$8B7A`는 `$7EB6 ≥ 20`과 **보상 후 경험치 ≥ 7000**을 검사한다. 통과하면 `$8BF5`의 `LDA #1; STA $7EB5`가 시간 기계 생성 요청을 남긴다.

[성 출구 경계 추적](../tools/trace_cas_princess_gate.py)은 같은 비공개 성 첫 입력 상태에서 출구 타일을 공주 분기로 바꾸고, 격추 수와 진입 경험치만 세 조합으로 설정했다. 긴 대사 호출 `$8AC1`을 `$8B38`으로 건너뛰었으므로 이 실험은 **수치 관문**에 한정한다. 보상·두 비교·플래그 쓰기는 원본 코드 그대로 실행했다. 격추 수 19, 경험치 6500은 보상 후 7000이어도 거절됐다. 격추 수 20, 경험치 6499는 보상 후 6999라 거절됐다. 격추 수 20, 경험치 6500은 보상 후 7000에서 `$7EB5:0→1`이 됐다. [검증기](../tools/verify_cas_princess_gate.py)는 세 실행의 스냅샷 계보·원본 바이트·진입 패치·분기·결과를 확인한다. 이 수치가 공략의 레벨 8과 어떻게 대응하는지, 실제 공주 구출의 선행 조건은 별도로 남는다.

야외 지도가 재구성될 때 `OUT $9565`는 `$7EB5`를 확인하고 `$7EA8 < 7`이면 위치를 고른다. `$958C`는 타일 코드 `$0F`를 `$9927`에 전달한다. `$9927`은 코드를 한 비트 왼쪽으로 밀어 야외 `$6000` 지도의 해당 셀에 원시 바이트 `$1E`를 쓰고, 동적 물체 목록에도 기록한다. 성공 여부와 관계없이 `$9591`은 `$7EB5`를 0으로 지운다. [탑승 분기](../disasm/OUT-board-transition.s)는 원시 `$1E`를 코드 `$0F`로 읽어 네 보석을 확인한 다음 `TM`을 선택한다. 기존 첫 야외 지도 스냅샷에는 이 탈것 타일이 없었다.

실행 검증은 이미 추적한 성의 왼쪽 출구에서 `OUT` 선택 직전 `$7EB5`만 `0→1`로 바꿨다. 재생은 `OUT $8956 → $9567 → $958C → $9927 → $9596 → $8A6C`에 도달했다. 후보 `(6,7)`의 원래 지도 바이트 `$04`가 `$1E`로 바뀌고 `$7EF6` 동적 물체 수가 `0→1`, `$7F97/$7F47/$7EF7/$7FE7`은 각각 새 타일·y·x·원래 타일을 기록했다. `$7EB5`는 0으로 돌아왔다. 같은 출구의 일반 실행과 `$6000–$6FFF` 전체를 비교하면 `(6,7)`의 **한 셀만** 달랐다. 스냅샷과 보고서는 비공개 `build/traces/final-craft-spawn/`에 있으며, 공개 검증기는 원본 추출물과 이 스냅샷을 로컬에서 사용한다.

따라서 현재 확인한 큰 흐름은 `성 의뢰 수락 → 랜드마크 방문/던전 몬스터 처치 → 성 보상 → 공주 경로의 탈것 요청 → OUT 지도 재구성 → 네 보석을 지닌 채 탑승 → TM`이다. 이 연결은 코드와 통제 실행을 합친 것이며, 처음부터 끝까지의 자연스러운 입력 경로는 아직 미확인이다. 특히 공주 경로의 선행 조건, 탈것 위치 선택의 실패/재시도, 다른 우주선의 정상 획득, 재방문 및 저장 후 상태를 다음 실행 과제로 남긴다.

`TM`에 들어간 뒤의 결말 관문도 별도로 검증했다. 통제 진입 후 동쪽으로 10회 이동해 보석 바로 옆 `(14,5)`에 도착하고 `G`로 `$95AB`를 1로 만들었다. `A` 다음 동쪽 방향키를 입력하면 몬데인의 체력이 1000→970으로 감소했다. 같은 입력 직전 몬데인의 체력만 1로 낮춘 통제 실험은 `$8FEE`을 거쳐 승리 경로 `$9034`에 도달했고, 보석 파괴 표시도 0으로 낮춘 대조 실험은 `$9033`에서 반환했다. 승리 경로는 `NIF`를 `$4000`에 정확히 로드했다. [검증기](../tools/verify_tm_victory_gate.py)가 입력·상태·분기·파일 일치를 검사한다. 자연스러운 전투 완주, `NIF` 데이터 형식, 화면 결말은 별도 과제다.

로드 직후 결말 루틴은 `$4000–$5FFF`의 8192바이트를 `$6000–$7FFF`로 옮기고 원본 영역을 0으로 지웠다. `NIF` 파일은 7680바이트이므로 끝 512바이트는 기존 RAM 내용이다. 이 실행에서는 그중 232바이트가 0이 아니었다. 이후 애니메이션과 `$9132` 입력 대기에 도달했고 Space를 누르면 `$914D → $912F`를 통해 대기로 돌아갔다. 포트에서는 8 KiB 이동과 남는 512바이트의 출처가 화면에 미치는 영향을 확인해야 한다.
