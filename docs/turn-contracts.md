# 한 턴의 공통 경계와 모듈별 차이

같은 Up 키(`$0B`)를 각 모듈의 첫 입력 스냅샷에서 재생했다. [비공개 추적 도구](../tools/trace_turn_contracts.py)는 키 반환부터 명령 검색, 동적으로 패치된 핸들러 호출, 루프 복귀, 다음 키 대기까지 PC를 확인하고 플레이어 상태·던전 좌표·메인 화면 RAM·프레임 해시를 비교한다. `build/traces/turn-contracts/comparison.json`은 Git에 넣지 않는다.

| 단계 | `OUT` | `DNG` |
| --- | --- | --- |
| 키 폴·반환 | `$8A6C → $8A74` | `$8DDA → $8DE4` |
| 공용 해석으로 들어가는 모듈 경로 | `$89CB → $89CE` | `$8DD4 → $8DD7` |
| 패치 호출·실제 핸들러 | `$89DC → $9357` | `$8E0B → $8E95` |
| 핸들러 복귀 | `$89DF` | `$8E0E` |
| 다음 루프·표시 | `$8995 → $89A1` | `$8DE6 → $8982` |
| 다음 키 대기 | `$8A6C` | `$8DDA` |
| 한 턴 뒤 변화 | 공유 영역 `$7E37,$7E4F,$7E50,$7EDB,$7EE4` | 던전 작업 좌표 `$A4E9`; 관찰한 `$7E00–$7FFF` 공유 영역은 변화 없음 |

두 모듈은 같은 키 해석기 `$82A2`와 간접 핸들러 방식을 사용하지만, 이동 좌표계와 화면 생성기가 다르다. `OUT`은 `$6000` 야외 지도를 참조하고 `$7E4F/$7E50` 등의 공유 상태를 갱신한다. `DNG`는 `$B099`의 11×11 작업 지도와 `$A4E8` 부근의 위치·방향 상태를 사용한다. 첫 Up 턴에서 던전은 `$A4E9`만 바뀌었고 HP·식량은 그대로였다. 이 결과만으로 모든 던전 턴이 자원을 소비하지 않는다고 일반화하지 않는다.

같은 도구로 `CAS`와 `TWN`의 첫 Up 턴도 재생했다. 두 모듈 모두 `$15C2` 입력 경로에서 공용 `$82A2` 해석을 거쳐 다음 폴로 돌아왔다. 성은 `$8A27 → $8A2F → $8A4A → $8A56 → $8A93 → $8A59 → $8A31 → $8A27`, 마을은 `$8A1E → $8A26 → $8A41 → $8A4D → $8A8A → $8A50 → $8A28 → $8A1E` 순서다. 다음 폴에서 두 모듈의 변경 주소 집합이 **공유 영역 `$7E4F,$7E50,$7EDA,$7EE4`와 zero page `$0001,$000C,$000D,$0072,$0073`로 정확히 같았다.** 이것은 2차원 지도 이동 프레임을 공유한다는 강한 실행 근거다. 값 자체와 지도 충돌 규칙까지 같다는 뜻은 아니다. 화면 RAM 차이는 각각 363바이트와 265바이트이고, 픽셀 해시도 각자 바뀌었다.

메인 화면 RAM `$2000–$5FFF`는 다음 폴에서 각각 5,420바이트와 5,998바이트가 시작 스냅샷과 달랐고, 프레임 픽셀 해시도 바뀌었다. 비교 구간에 다른 표시·프레임 작업이 섞여 있으므로 이 수를 Up 명령 단독의 픽셀 효과로 해석하지 않는다. 현재 차이를 찾은 주소는 메인 RAM 기준이며 보조 RAM/소프트 스위치/스피커 출력을 포함하지 않는다. 다음 정밀 단계는 핸들러 경계에서 메모리 쓰기 이력을 좁혀 타일·문자·애니메이션 효과를 분리하는 것이다.

## 오버레이 진입 증거

`OUT` 첫 입력 스냅샷에서 공용 선택기 `$88FD`에 선택값을 제어한 초기 실험도 있다. `SPA` 선택값 `$14`는 9,930바이트 전체가 추출 파일과 일치했고 `$8956 → $8A53 → $8A5F`를 실행했다. `TM` 선택값 `$18`도 8,123바이트 전체가 일치했다. 이 첫 실험에서는 시작 연출의 Space 입력을 보내지 않았고, 루프를 보기 위해 PC를 `$8E5E`로 주입했다. [초기 선택기 실험](../tools/probe_overlay_loops.py)의 결과는 아래 실제 B 명령 실험과 구분한다.

한 단계 더 실제 입력에 가깝게 `OUT` 폴에서 **B** 키를 보냈다. 보통 상태의 현재 타일 코드는 `$01`이며 `$8D1F`의 탑승 거절 경로를 탔다. 통제 실험은 `$7E7C=0`(미탑승)에서 **현재 지도 셀만** 원시 값 `$1C`(코드 `$0E`, 선택값 `$06`)로 바꿨다. 같은 B 입력이 `$8CF0 → $8D14 → $8D42 → $8D6E → $88FD(A=$14) → SPA $8956 → $8A53`으로 이어졌고 SPA 파일 전체가 일치했다. 다른 실험은 셀을 `$1E`(코드 `$0F`, 선택값 `$0A`)로 바꾸고 `$7E75–$7E78` 네 바이트를 모두 1로 놓았다. B 입력이 `$8D73 → $88FD(A=$18) → TM $8956 → $8AD7`으로 이어졌고 TM 파일 전체가 일치했다. [탑승 경로 재현](../tools/probe_out_board_transitions.py)과 [45바이트 분기 소스](../disasm/OUT-board-transition.s)를 제공한다. 탈것 획득과 네 플래그를 정상 게임 플레이에서 달성하는 경로는 아직 찾지 못했다.

`TM` 시작은 공용 “Press Space to continue” `$87F7 → $881B`을 **네 번** 지난다. [첫 페이지 입력](../tools/trace_tm_page1.py)은 A=`$20` 반환과 `$882A` 수락을 확인한다. [나머지 세 페이지](../tools/trace_tm_intro_pages.py)도 각각 `$881B → $881E(A=$20) → $882A`를 지난 뒤 실제 `$8E5E` 루프와 첫 `$9815` 입력에 도달했다. 따라서 TM 메인 루프의 자연스러운 **모듈 내부 실행**은 확인됐다. 탈것과 네 플래그를 통제한 출발점이므로, 이 실험만으로 정상 플레이가 결말에 도달할 수 있음을 입증하지는 않는다.

| 입력·반환 | `$8A5F → $8A62` (`$15C2`) | `$9815 → $8E83` (자체 `$9827`, `$15C8/$15BF`) |
| 공용 해석 결과 | `$8A6A`, X=`$08` | `$8E91`, X=`$08` |

[SPA 턴 추적](../tools/trace_spa_first_key.py)과 [TM 턴 추적](../tools/trace_tm_first_key.py)이 메인 RAM 화면 바이트 및 프레임 해시도 기록한다. 이 턴에서 각각 410바이트와 216바이트가 시작 화면 RAM과 달랐다. 그 차이에는 명령 외 표시 작업이 포함된다.

## 메모리 수명 표본

[메모리 관찰 도구](../tools/inspect_memory_lifetime.py)는 각 모듈 첫 입력의 비공개 스냅샷을 복원한다. `$8956`에는 각각 `OUT` 5,228/5,230, `CAS` 5,518/5,524, `TWN` 8,456/8,461, `DNG` 10,022/10,051바이트가 파일과 일치했다. 차이는 주로 실행 중 패치된 명령·상태 영역이다. 공용 엔진 `$7000–$8955`는 각 시점에 6,402–6,408/6,486바이트가 초기 파일과 일치했고, `STUPH` `$0800–$1FFF`는 6,058–6,101/6,144바이트가 일치했다. **파일과 다른 바이트를 무조건 손상으로 판단하지 않는다.** 이름·플레이어 상태·자기 수정 코드가 RAM에서 바뀐다.

`$6000–$6FFF` 해시는 `CAS`·`TWN`·`DNG`에서 같고 `OUT`에서는 달랐다. 이는 해당 표본에서 이 영역의 내용이 세 장면 사이에 유지됐다는 관찰이다. 이 영역의 모든 소비자와 쓰기 시점을 아직 규명하지 못했다. `$B000–$B6FF` 해시는 네 장면에서 모두 달라 작업 지도/버퍼가 오버레이별로 재사용됨을 보여준다. 해시 일치·차이만으로 각 바이트의 의미나 영속 저장 여부를 판정하지 않는다.
